# 初めに
この記事では製作中の学園シミュで使用するライブラリの１つである Common を解説します。

# Common ライブラリ
Common は他ライブラリ間の依存関係を整理するためのライブラリである。

## 構成
このライブラリは構成する要素が非常に多い。ここでは比較的多くのライブラリに参照される要素のみ記載する。

|ユニット|機能|
|---|---|
|NPCProfile|NPCクラス|
|FullName|名前|
|Traits|性格|
|Club|部活|
|Gender|性別|
|Secret|秘密クラス|
|ユーティリティ系|MathUtil、RandomUtil|

## 依存するライブラリ

このライブラリは他に依存しない。

# 解説
Common には他のライブラリが使うデータや構造体と小さいユーティリティしかないため、これといって解説できることが無い。

そのためここではライブラリ間の依存関係に触れ、Common ライブラリの存在意義を書いておくことにする。

## Common
まず今回のプロジェクト全体を通して、ライブラリ開発において重要視しているのが次の２点である。

- 責務
- 依存関係

これだけ押さえておけばプロジェクトが肥大化しても破綻し辛い。

所謂 "単一責任の原則" に従って開発しているため、個々の責務に関しては大きな問題にならない。

問題になるのはライブラリを接続していった場合の依存関係である。

### 循環依存の何が悪いのか

一般論で語るほどの知識は無く、かといってついでに書くには大きすぎる問題なので、現在意識してることをすこし述べておく程度にする。

【循環依存があると...？】
- プロジェクト全体の見通しが悪くなる
- ビルドの不安定化
- 再利用性の低下

一言で言うと "システム全体の設計が壊れる"

以下補足。

【プロジェクト全体の見通しが悪くなる】

先ほどの例のように少ないライブラリ数であれば良いが、多数のライブラリを作ることが予想される場合、依存方向を整理しておかないとあっという間に破綻してしまうだろう。

ライブラリを修正した場合も、その修正がどこまで波及するかもわかり辛くなる。

【ビルドの不安定化】

これはインクルード周りで起こりやすい問題である。簡単に言うとインクルードが相互参照して地獄を見る。<br>
前方宣言で逃げれればよいがそうもいかない場合は構造から循環依存を切る必要が出てくる。

コードは正しいのになぜかビルドが通らないといった問題もこのインクルード周りが原因だったりすることがある。

【再利用性の低下】

ライブラリは別のプロジェクトで流用する可能性がある。このとき単一のライブラリで機能が閉じていれば再利用しやすい。

## 注意点

- 別ライブラリを参照しないこと
- なんでもかんでも Common に含めないこと

1つ目は当然、このライブラリが他を参照し始めたら意味がない。例外的にライブラリを分割した場合とかはあり得るかもしれないが。

2つ目は "便利ライブラリ" にし過ぎないこと。

構造上ほとんどのライブラリが Common を参照するが、可能であれば参照させないに越したことはない。<br>
ここで管理するデータは慎重に選ぶ必要がある。

# テスト
このライブラリ単体では機能しないため、個別のテストは行っていない。最低限ビルドが通って .lib が生成されていれば良い。

別のライブラリと Common の連携確認を以ってテストとしている。

このライブラリは他と比べて特殊な立ち位置ですが、システムを構築するうえで重要な役割を持っています。
