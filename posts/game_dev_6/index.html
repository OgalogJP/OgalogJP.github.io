学園シミュ Lib開発 Conversation

2026年8月25日

初めに#

この記事では製作中の学園シミュで使用するライブラリの１つである Conversation を解説します。

Conversation ライブラリ#

Conversation は Player 対 NPC や NPC 同士での会話を実行するライブラリである。

関連するライブラリ#

  • Common
  • Social
  • Service

解説#

このゲームの会話は大きく分けて 2 種類存在する

  • NPC 同士の雑談
  • Player 対 NPC の会話

現時点で実装済みなのは NPC 同士の会話のみ。

Player 対 NPC の会話は UE 側からのアクションが必要であるため一旦後回しになっている。実装後改めて追記する。

ライブラリの目的#

このライブラリの目的は会話ロジックを外部で完結させ、UE 側ではテキスト表示のみに専念させるためである。

構造#

会話を実現させるための構造は以下の通り。

  • ConversationSession
    会話の往復管理や会話に参加している生徒の管理、発言内容の保存など、会話の状態を管理する構造体

  • 会話内容の json
    会話は json を使用したデータ駆動で行われる

  • ConversationManager
    会話ライブラリの中核であり、会話テキストの選択、会話モジュールの管理などを行っている

  • 会話 state machine
    会話の種類を自由に増やせるよう、会話は state machine で管理している

会話の発生条件#

  • NPC 同士が近づいたとき、確率で発生
  • Player が NPC に話しかける

会話の種類#

現時点では json テンプレートからランダムに選択して構築された雑談しか実装していないが、仕様上いくらでも増やすことができる。

会話を追加する場合の手順は次の通り。

  • 会話タイプ enum に新規会話タイプを追加
  • Conversationmanager に会話モジュールを追加
  • 会話 state machine に新しい会話への分岐を追加

会話の種類ごとにモジュールを区切ることで、会話独自の実装を行えるようになっている。

会話の種類独自処理
雑談会話に参加した生徒の関係値更新
秘密秘密・噂に関する会話
クエストクエスト報酬の付与
ユニーク共通処理では行えない独自処理
ストーリー決まった内容・順序で進む

会話の流れ#

  1. なんらかのアクションで会話発生
  2. 会話 session 作成
  3. 会話参加者内で会話の順番と会話の最大ターンを決定
    だれが話し、それに対して誰が返すか、それを何回繰り返すかを決める
  4. 会話中、session 内の会話ログに今回の会話内容が記録される
  5. 会話終了後、session 内の会話ログを UE に上げ、会話テキストを順次表示させる

実装途中に検討したこと#

唐突ですが、ここで会話ライブラリ設計に関する小話をしたいと思います。

今回会話処理を データドリブン、state machine、会話モジュールという形で実装しましたが、検討事項が2つありました。

自然言語処理は断念#

実装途中、会話内容を自然言語処理(厳密には形態要素分析)で構築しようと既製の外部ライブラリである mecab を試みました。

mecab に至ったのは完全に AI にそそのかされたからですが、思った以上に mecab は難敵でした。まずネット上に転がってる既製のライブラリは 32bit 版であり、64bit 環境では使えません。そのためソースから 64bit 版を構築しなければなりませんが、これが非常に厄介な作業でした。

ちなみに mecab は 2 種類有り、1 つは単体で機能するもの、もう 1 つは外部 dll として既存プロジェクトに混ぜて使えるタイプのもの。今回欲しいのは後者ということになります。

AI と共闘した結果無事 64bit 版 dll を生成でき、既存プロジェクトとの接続も可能という段階に来ました。

しかしライブラリ単体で色々試すうち、これは余りに規模が大きいライブラリであると感じ、採用を見送りました。

大きい問題は日本語という言語に対する私の認識不足です。特に今回生徒同士の会話ということで、常に正しい日本語で話すとは限らない点や若者言葉の難しさがネックになります。

これはもはや研究と言えるレベルであり、ゲーム制作のついでで扱うような内容ではないと判断しました。

LLM は使わない#

この AI 時代、当然検討すべき内容として LLM の使用が挙げられます。

LLM の不使用は早い段階で決定しました。

自然言語処理の場合とは違い、こちらは実際に試して断念というわけではなく、一般的に知られる特徴から判断した形になります。

懸念点は以下のようなものが挙げられます。

  • 正確性
  • プロンプト・制約の決定

私のこだわりですが、会話は雑談含め常に意味のあるものにしたいと考えています。存在しないものが会話に出てくるとゲームに対する不信感につながります。例えば “体育館って会話で出てきたけど体育館なくね ?” みたいなことが続くと、会話内容が信用ならなくなります。

プロンプトの決定や実際の会話生成にも課題があります。会話を生成する前にどういう内容で作るかを指示しますが、内容の整合性が取れてるかどうかは生成してみないとわかりません。
であれば予め会話テンプレートとしてある程度整合性が取れた内容を用意し、ランダムで選ばせ会話を構築したほうが良いと考えました。

テスト#

  • 生徒 id = 0 ~ 9 を会話に参加させる
  • 会話の最大ターンをランダムで決定
  • 会話させる
  • 関係値の条件達成で会話の遷移(今回は秘密・噂に関する会話)

実行結果#

会話の参加者と発言順序

雑談から秘密に関する話に遷移する様子

※ 登場する生徒名は実在の人物と関係ありません

まず会話に参加する生徒と、会話の順番を決定する。その後決められた順序で会話が進められる。この時点では実際に会話が何ターン続くかは決定していない。

順序決めの後、実際に何ターン会話するかが決定し会話が進められる。
会話の最大ターンを後で決定しているのは関係値が高い同士( = 仲が良い)程、会話が長く続くという状態を表現している。

今回は会話後に関係値が一定以上になり、別の会話に遷移した。もし遷移しなかった場合、最大で9ターン雑談が続く。

終わりに#

今回は Conversation の構造を整理・解説しました。

会話ライブラリは現在制作中のライブラリの中でも特に巨大なライブラリになっています。

目標であった会話ロジックをライブラリに閉じ込めて結果だけをUEに送る構造は完成していますが、まだ未実装の部分が多く残っている状態です。

Player 対 NPC の会話実装と UE との接続後に改めて実際の動きを見せれればと思います。
